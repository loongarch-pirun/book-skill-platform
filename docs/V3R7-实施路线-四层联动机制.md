# V3-R7 实施路线——智能体 × 知识库四层联动机制

> 2026-10-19。上游文档：《V3R7-模型可见性改造-审计与方案.md》（缺口审计）、《凤凰架构实战验证报告.md》（四层验证）。
> 本文回答的问题只有一个：**怎么改、按什么顺序改，才能让「未来每一本书」都自动获得联动能力，而不是只修凤凰架构这一本。**

---

## 一、结论先讲

1. **这次改的是机制，不是某一本书。** 把能力拆成四层各建一次——数据层（建库期）、工具层（MCP 契约）、行为层（技能动线）、验收层（新书门禁）——之后每本新书入库即插即用，零额外适配。
2. **优先级四批，每批独立可回退**：第 1 批数据层 + get_outline（地基）→ 第 2 批 read_full_book + token 闸（分流）→ 第 3 批 cite_check + 桌面对称（可信闭环）→ 第 4 批技能沉淀 + 考卷重建（行为固化）。
3. **检索引擎零改动。** eval 93 基线不动；每批都有回退开关；每批半天级工作量。
4. **真题是问题，不是书。** 联动闭环 = 真题/工作问题进来 → query_library 自动挑书（已有）→ 需要引用论证时走标准动线 → 答案沉淀成技能。第 4 批考卷重建按新动线出题。

---

## 二、四层机制总览

| 层 | 建什么 | 建一次之后 |
|---|---|---|
| L1 数据层 | 每本书入库时自动产出「地图 + 体量账 + 卫生拦截」 | 存量 8 库跑一次回补脚本；未来新书建库即带 |
| L2 工具层 | get_outline / read_full_book / cite_check 三个通用 MCP 契约 + token 闸 | 所有书一视同仁，无书名硬编码 |
| L3 行为层 | 「用知识库论证」的标准动线沉淀成技能（save_skill） | 任何智能体接上 MCP 就会走同一条动线 |
| L4 验收层 | kb-e2e 泛化验收 + 新书五步绑定 | 每本新书即插即用有机器证明 |

一句话：**L1 让书自带地图，L2 让模型有路可走，L3 让智能体会走路，L4 保证每本新书真的走通。**

## 三、L1 数据层——每本书入库时自动产出（第 1 批）

### 3.1 build-book.js 建库时写三个 meta 键

现行 meta 已有 `chunk_count / total_chars / num_chapters`（实测 mengzi：743 块 / 44,973 字 / 261 章）。新增：

| meta 键 | 算法 | 用途 |
|---|---|---|
| `total_tokens` | `total_chars × 语言系数`；系数按抽样 200 块 CJK 率自动判：CJK 率 ≥0.2 → 0.75，否则 0.25 | read_full_book 闸门判断；list_books 展示体量 |
| `chapter_quality` | JSON：`{coverage, avg_name_len, verdict}`。coverage = 非空 chapter 块占比；verdict：coverage<0.5 → none；avg_name_len>30 或 coverage<0.9 → messy；否则 reliable | get_outline 按书的质量决定展示策略 |
| （顺带）排除 `_private/` | md 目录扫描时跳过任何以 `_private` 开头的路径段 | 作者简历类污染每本书都可能带，GG 护栏还保护它，清洗删不掉——必须在入口拦 |

语言系数已用实测校准：P&P 710,791 字符 × 0.25 = 177.7K token，与审计账吻合。

**章节质量实测**（本轮查库）：

| 书 | chapter 列现实 | verdict |
|---|---|---|
| 凤凰架构 md | 416 个叶子章，`chapter`=叶子名，`chapter_path`="父 › 叶" | reliable |
| P&P epub | 16 个"章"，但值是正文片段（如 "I hope Mr. Bingley will like it. CHAPTER II."） | messy |
| attention pdf | 全 null | none |

### 3.2 存量回补脚本 `src/backfill-meta.mjs`

- 对 `library/*.db` 只读打开算、读写打开补写 meta 三键；**不重切片 → 编目边不作废 → 不需要 --force**
- 幂等：已存在且值相同则跳过；跑两遍结果一致
- 同时是 list_books 的兜底：meta 缺 `total_tokens` 时 listBooks() 现场用 `total_chars × 系数` 算，未回补的书也立即可见

### 3.3 验收（第 1 批门禁）

- `get_outline` 对 8 库全部正确：md 出层级、epub 标 messy 并提示、pdf 优雅降级 no-chapters
- 回补脚本幂等（跑两遍 diff 为空）
- guard-test 新增：outline 工具存在性 / FULL_READ_TOKEN_CAP 常量 / 回补不碰 chunks 表
- `npm run test:fast` 全绿；stage3-mcp-test 工具数硬断言 14→16 同步

## 四、L2 工具层——三个通用契约（第 2、3 批）

### 4.1 `get_outline(book)`——翻书动线的第一跳（第 2 批）

```sql
SELECT chapter, chapter_path, COUNT(*) blocks, SUM(length(text)) chars, MIN(id) first_id
FROM chunks WHERE chapter != '' GROUP BY chapter ORDER BY MIN(id)
```

- 返回：章名 + 每章块数 + ≈token + 本书 chapter_quality；md 书附 chapter_path 层级
- 响应上限 maxChapters（默认 100，最多 500），超出给 note「还有 N 章未列出，用 read_range 按块号翻」
- **为什么它最高优**：凤凰验证实测——「分布式事务」顶层章仅 2 块，模型没有地图永远发现不了这块；而 528 章路径的书靠猜是死路

### 4.2 `read_full_book(book)`——小书全文直读（第 2 批）

- token ≤10K（`FULL_READ_TOKEN_CAP`，browse.mjs 同款导出常量供 guard 断言）→ 全文按块序端出：论语 0.5K / 道德经 5.6K / attention 9.6K 四本立即受益，**质量上限从检索天花板变成全文天花板**
- >10K → `{error:"too-big", tokens, hint:"用 get_outline + get_chapter/read_range"}`——「权限全开」的正确形态：**闸门按书体量自动开关，不是人工维护白名单**

### 4.3 browse cap 改 token 闸（第 2 批）

- `estimateTokens(text)`：CJK 字符 ×0.75 + 非 CJK ×0.25 现场估算
- `CHAPTER_TOKEN_CAP = 8000`：readChapter/readRange 按 token 累计截断，续读游标按 token 给；块数 cap（60/80）保留作硬上限
- 返回体带真实 token 账——模型能自己算账，消耗可预算
- 修工具描述：按 chapter 列实际覆盖率重写 get_chapter/read_range 描述（现描述写「EPUB 章节值不可靠」把调用方劝退，但 P&P 是 messy 不是 none，read_range 才是它的正路）

### 4.4 `cite_check(book, quote)`——防幻觉闭环（第 3 批）

- 给定引文，回库逐字找：命中返回 `{hit:true, chunk_id, chapter, page}`，未命中 `{hit:false}`
- 把桌面 verifyAnswer 的引用逐字回源红线**工具化**——外部智能体写完答案可以自检，凤凰 e2e 已验证「差一字即拦」
- v1 精确子串匹配；子句级命中率作 v2

### 4.5 桌面对称：cloudSummary 小书全文模式（第 3 批）

- bookId 指向的书 token ≤10K → 跳过检索，全书作 passages 进 askCloud（引用回源天然成立）
- 开关 `BSP_FULL_READ=0` 回退；chat-fuzz 的 reqCount 精确断言按既有惯例隔离

## 五、L3 行为层——标准动线沉淀成技能（第 4 批）

用 save_skill 落一个 `kb-research` 技能（skills/daodejing 是现成先例），内容就是智能体与知识库联动的「操作系统」：

```
① list_books      → 看有哪些书 + 每本 total_tokens（体量分流）
② 分流            → ≤10K：read_full_book 直读；>10K：get_outline 看地图
③ 定位板块        → get_chapter 整章通读 / read_range 按块号区间读 / query_book 检索兜底
④ 引用            → 原文照抄 + 行尾标〔书名·章节〕；引用前 cite_check 回验
⑤ 书中没有的      → 诚实报告「无依据」，不许编造
```

第 ⑤ 条是凤凰 e2e 用真案例换来的：问「订单库分片策略」，书中没有，模型明确报告无依据拒绝编造——**智能体辅工作的价值一半在找得到，一半在不瞎编。**

## 六、L4 验收层——每本新书即插即用（第 4 批）

- `books/_work/fenix-e2e.mjs` 泛化成 `kb-e2e <db>`：search / browse / cite / e2e 四模式原样保留，参数化到任意书
- 写进《新书接入验收流程.md》成必跑步骤（新书五步之后）
- 考卷重建（kk 正式收录时）加两类题：全文直读 vs 检索对照题（量化小书收益）；动线题（考模型会不会用 get_outline→翻章→cite_check，不只考检索准不准）

## 七、执行顺序与每批交付物

| 批 | 内容 | 文件 | 回退开关 | 验收 |
|---|---|---|---|---|
| 1 | L1 数据层 + get_outline | build-book.js / 新建 src/lib/outline.mjs / register-tools.mjs / backfill-meta.mjs | 工具可摘除，无引擎影响 | outline 8 库正确 + 回补幂等 + guard 新增断言 + fast 全绿 |
| 2 | read_full_book + token 闸 + list_books token 列 | browse.mjs / search.mjs / register-tools.mjs | FULL_READ_TOKEN_CAP / CHAPTER_TOKEN_CAP 常量 | 四小书直读 + 大书正确拒绝 + token 账可见 |
| 3 | cite_check + cloudSummary 全文模式 + 描述更新 | 新建 cite 检查（复用 search 字面腿）/ chat.mjs / 工具描述 | BSP_FULL_READ=0 | 假引文被拦 + 桌面小书全文模式 + chat-fuzz 隔离 |
| 4 | kb-research 技能 + kb-e2e 泛化 + 考卷重建 | save_skill 落盘 / kb-e2e.mjs / 验收流程.md | 技能可删 | 新书五步必跑 e2e + 考卷按新动线出题 |

**排序逻辑**（为什么不是先做简单的 read_full_book）：数据层是所有工具的地基且对存量+未来一次性覆盖；outline 是全部动线的第一跳，凤凰实测证明它是最高优缺口；小书直读质量跃升大但影响面只有四本小书；可信闭环和桌面次之；行为固化必须等真真题/新书才有意义，空转写技能是无米之炊。

## 八、改完之后的样子（token 账）

| 场景 | 现在 | 四批之后 |
|---|---|---|
| 小书问答 | 检索 top-6 ≈2K + 排序误差风险 | read_full_book 0.5~10K 全文，零检索误差 |
| 大书问答 | 检索 top-6，模型不知道书里有什么 | get_outline 看地图 → get_chapter/read_range 翻目标章 → 检索兜底 |
| 引用论证 | 只有桌面链路有 verifyAnswer | cite_check 工具化，任何智能体可自检 |
| 新书入库 | 每本单独看cap不cap | 建库即带地图+体量账，五步+e2e 即插即用 |
| 全库 | 一次 333K 全喂 = 爆炸 | 按书自动分流，没有任何场景需要全喂 |
