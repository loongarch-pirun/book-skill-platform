# 模型清单与包体基线（唯一事实源）

> **本文件是模型配置与包体体积的唯一口径。** 与 README、旧 docs、旧日志冲突时，以本文件为准。
> 建立于 2026-11-16，全部数字为当日实测，非估算、非沿用旧文档。

## 0. 结论（先看这里）

1. **README 的「不上传任何内容到云端」与代码不符。** 检索在本地，答案生成走云端 OpenAI 兼容 API（`src/lib/llm.mjs`）。检索出的原文块会作为提示词发往云端端点。当前是**混合链路**，不是纯本地。
2. **安装包 1.80 GiB（1.94 GB）。2026-11-18 用户拍板：预算线改 2.0 GiB 认现状，1.80 在新线内（0.9 倍）。** 旧 1.1G 回退线（出处 `docs/收官打包与交接规划-2026-10-21.md:190`）已 superseded。
3. **体积第一大头是 PDF 解析（1.67 GB），不是模型（1.24 GB）。** 模型已用 int8 / q8 最低可用量化档，没有更小的档可换。
4. **「内容零上传 + 单包 ≤1.1G + 保留 PDF」在旧 1.1G 线下无解（历史物理分析，保留）。** 2026-11-18 单包线已改 2.0G 认现状，体积不再是被约束项；零上传与否另由问题1方向决定（准确优先·同意发片段），与包体线无关。

> **更正记录（2026-11-16）**：本文初版把 `.models` 目录总量 2.96 GB 与 reranker 目录总量 1.71 GB 当成了「进包体积」，是错的。目录里含 `model_q4.onnx`（1,194.5 MB），该文件被 `build.extraResources` 的 filter 排除，不进包；代码也用 `dtype:"int8"`，不读它。实际进包模型为 **1.24 GB**。以本节及第 2 节为准。

> **预算线决策（2026-11-18）**：用户拍板「改预算线认现状」——单包上限 1.1→2.0 GiB，保留离线开箱即用 + PDF 导入 + 本地模型三件套，承认 1.80 GiB 的物理现实。`size-budget.json` 的 `budget` 块已同步（status ok / ratioToLine 0.9）。下文所有「1.1G 线失守/互斥」论述为旧线下的历史分析，只作归档，不再作为当前结论。

## 2. 为什么「零上传」这条路走不通

### 2.1 当前链路实际是什么

```
提问 → 本地检索（bge-m3 int8 向量 + bge-reranker int8 重排）→ 取出原文块
     → 【云端】OpenAI 兼容 API 生成答案 → 引用校验 → 返回
```

`src/lib/llm.mjs` 文件头自述为「V2 云端问答引擎层（P1）……调 OpenAI 兼容 API」。
**书中的原文片段会离开本机。** README 原第 8 行与第 150 行的「不上传任何内容」是错的，已改。

### 2.2 改成真正零上传要付什么代价

本地生成必须补一个生成模型。当前包里**没有任何生成模型**：

- 1.2B 级 VLM 曾评估过，结论是「可选下载、不进主包」
- 若强行进包，按同量级推算再加 1~3 GB
- 加完之后包体在 1.80 GiB 之上继续变大，1.1G 线彻底失守

**结论：零上传与 1.1G 单包是两个互斥目标。** 当前实现选了「生成上云」换体积，但 README 一直没这么说。

## 3. 体积为什么压不下去

已知的 3,040.6 MB 里，**模型已经没有余量**：

- 四个模型全是 int8 / q8 量化档，已是可用最低档
- 换更低精度没有现成文件；q4 那个 1.19 GB 的文件比 int8 还大，是废档
- 备选向量 e5-small + bge-small-zh 合计 152.2 MB，砍掉只省 0.09 GiB，不够看；而且降级路径会断

**真正能动的是 PDF 解析那 1,671.0 MB。**

### 3.1 三条可走的路

| 方案 | 未压缩可省 | 压缩后约省 | 能否压到 1.10 GiB | 代价 |
|---|---|---|---|---|
| 去掉 PDF 导入（砍 mineru 前后端） | 1,671.0 MB | ~1,064 MB | **能**（降至约 0.87 GiB） | 不支持 PDF，产品能力缺口 |
| 模型移出安装包，首次运行下载 | 1,271.2 MB | ~810 MB | **能**（降至约 1.05 GiB） | 不再开箱即用，首次需联网取模型 |
| 拆完整版 / 精简版双包 | 精简版为主 | — | 能 | 维护两份产物与两条回归链 |

### 3.2 走不通的路

| 想法 | 为什么不行 |
|---|---|
| 模型再降精度 | 已是 int8/q8；q4 文件更大且代码不读 |
| 只砍备选向量 | 只省 152 MB，不够 |
| 压缩算法再调 | 已 1.57:1，LZMA 到头，收益 <5% |
| 保留 PDF + 保留模型 + 1.1G | 数学上不成立：两块合计 2,942.2 MB，压缩后约 1.87 GiB，必然超线 |

## 4. 判决

| 条件组合 | 可行性 |
|---|---|
| 零上传 + 单包 ≤1.1G + 保留 PDF | **不可行** |
| 零上传 + 砍 PDF | 需再补本地生成模型（+1~3 GB），仍然不可行 |
| 生成上云 + 砍 PDF + 单包 ≤1.1G | 可行，代价是不支持 PDF |
| 生成上云 + 模型外置 + 单包 ≤1.1G | 可行，代价是首次需联网 |
| 生成上云 + 保留 PDF（现状 1.80 GiB） | 可行，但要把 1.1G 线改成真实数字，并改掉 README 的零上传承诺 |

**往下走只做一件事：在「砍 PDF」和「模型外置」之间选一个，或把 1.1G 线改成 1.8~2.0 GiB 的真实预算。三条都不选，就不要再提「压到 1.1G」。**

## 5. 如何重测（任何人可复现）

```powershell
# 安装包体积
Get-Item "release\BookSkillPlatform Setup 0.1.2.exe" | Select Length

# 进包模型（严格按 extraResources filter 口径，排除 q4）
$m=".models"
@(
  @{d="Xenova\bge-m3"; f="onnx\model_int8.onnx"},
  @{d="Xenova\multilingual-e5-small"; f="onnx\model_int8.onnx"},
  @{d="Xenova\bge-small-zh-v1.5"; f="onnx\model_quantized.onnx"},
  @{d="onnx-community\bge-reranker-v2-m3-ONNX"; f="onnx\model_int8.onnx"}
) | ForEach-Object {
  $p = Join-Path $m ($_.d + "\" + $_.f)
  "{0,-50} {1,8:N1} MB" -f $_.d, ((Get-Item $p).Length/1MB)
}

# PDF 解析前后端
"runtime\mineru-python","runtime\mineru-models" |
  ForEach-Object { "{0,-28} {1,9:N1} MB" -f $_, ((Get-ChildItem $_ -Recurse -File | Measure-Object Length -Sum).Sum/1MB) }
```

机器可读版本：根目录 `size-budget.json`。
