## 一、开源调研结论（2026-10-21 实查）

**1. Anthropic 官方三级渐进披露（agentskills.io 规范同源）**

| 级别 | 内容 | 加载时机 | 成本 |
|---|---|---|---|
| L1 | YAML frontmatter（name + description） | 启动时常驻 | ~100 token/个 |
| L2 | SKILL.md 正文 | 描述命中任务时 | <5k token / <500 行 |
| L3 | references/ scripts/ assets/ | 正文指引按需读/执行 | 0 直到被访问 |

**2. 社区硬规则（skills-guides.com / getclaudeskills / claudeskills.info 三处交叉一致）**
- description 是唯一的 L1 触发线索：必须同时写「干什么 + 何时用 + **不用于什么**（负面触发）」，第三人称，≤1024 字符单行
- name：kebab-case、≤64 字符、不含 claude/anthropic、与文件夹同名；社区惯例动名词（verb-ing）
- SKILL.md 必须精确命名；skill 目录内**不放 README.md**
- references 只深一层；>100 行的参考文件顶部加目录
- **确定性操作必须脚本化**（scripts/ 执行而非读入上下文，只有输出进上下文）
- allowed-tools 做最小权限声明
- 每个 skill 必须带 2-3 个具体 input/output 案例；解释 WHY 优于堆 MUST
- 交付前做**触发测试**：列 3-5 句「应触发 / 不应触发」的真实问法逐条验

**3. 可借鉴的开源技能**（不照搬，取设计思想）
- `rag-architect`（alirezarezvani/claude-skills）：检索管线的分块/嵌入/路由决策框架——对应我们建库侧的范式
- Addy Osmani agent-skills：Define→Plan→Build→Verify→Review→Ship 的工程工作流封装——「一族技能覆盖一条工作流」的组织方式
- VoltAgent context engineering：上下文预算意识——直接支撑议题二的用量治理
- obra/superpowers：技能原语化 + 组合调用

## 二、议题一：Skill 体系重构

### 2.1 现状盘点（本地实况）

- `skills/kb-research/` 已是规范结构：SKILL.md（五步动线）+ chapters/（ch01-ch03）+ glossary.md + cheatsheet.md + 原文锚点；`save_skill` 三道质检在岗；skill-state.json 管开关
- **此前的「12 个平级 skill」提案作废**，三个硬伤：
  1. **触发重叠**：架构调研/论文精读/概念对照/云选型四个都吃架构书，描述稍像就互相抢触发
  2. **无负面触发**：没写「不用于什么」，agent 会过度加载
  3. **无脚本化/预算意识**：深读类操作（read_full_book/get_chapter）是 token 大头，技能层没有任何约束

### 2.2 重构方案：从「12 个平级」改为「4 技能族 + 2 元技能」

| skill | 处置 | 能力域 | 吃的书 | 触发词（description 核心） |
|---|---|---|---|---|
| `kb-research` | **改建**（保留五步动线骨架） | 通用研究默认路径 | 全库 | 「定方案/找依据/引用论证」；负面触发：纯编码执行、实时信息 |
| `engineering-research` | 新建 | 架构调研/代码学习/论文精读/概念对照/云选型五个**场景模块**（cheatsheet 模式，不拆五个 skill） | 系统设计入门/凤凰/Dynamo/Lamport/MapReduce/OG-AWS/Attention/d2l/Hello 算法 | 「架构/系统设计/代码怎么实现/论文讲什么/某概念对比」 |
| `humanities-reading` | 新建 | 经典主题检索/小说人物情节/英文共读三模块 | 论语/孟子/道德经/简爱/P&P/弗兰肯斯坦/福尔摩斯 | 「某主题在经典里怎么说/人物情节/英文原著段落」 |
| `opinion-archaeology` | 新建 | kk 观点考古（问帖答帖分离、楼层引用） | kkndme | 「kk/楼主/当年怎么看」；负面触发：非 kk 书的话题 |
| `citation-check` | 新建（元技能） | 引文回验：贴回原文逐字验 + 上下文 | 全库 + cite-check lib | 「引用/佐证/出自/核对原文」；**脚本化优先** |
| `book-intake` | 新建（元技能） | 新书验收七关流程单 | 元技能 | 「加新书/入库/验收」 |

**关键决策**：工程向五个场景**不拆成五个 skill**——合成一个技能族内的场景模块（kb-research 的 cheatsheet 已验证此模式），从根上消除触发重叠；真正触发边界清晰的（kk、引文核查、新书验收）才独立。

### 2.3 每个 skill 的建造规范（对照开源硬规则）

```
<skill-name>/                  # kebab-case，与 frontmatter name 一致
├── SKILL.md                   # <500 行；L2 正文
├── references/                # 只深一层；>100 行加 TOC
│   └── <module>.md
├── scripts/                   # 确定性操作脚本化（如 cite_check 封装）
└── assets/                    # 输出模板（摘要格式单、出处标注格式）
```

frontmatter 模板：

```yaml
---
name: engineering-research
description: 工程向研究技能：架构调研、代码学习、论文精读、概念跨书对照、云选型参考。
  使用场景：设计架构、查代码实现、读论文、对比概念讲法、查 AWS 模式时使用。
  不用于：人文经典检索（用 humanities-reading）、kk 观点（用 opinion-archaeology）。
metadata:
  version: 1.0.0
  category: engineering
allowed-tools: [list_books, list_catalog, get_theme, query_book, query_library,
  similar_chunks, get_outline, get_chapter, read_range, cite_check]
---
```

### 2.4 验收标准（每技能）

1. `save_skill` 三道质检全过（现有机制）
2. **触发测试**：5 句应触发 + 5 句不应触发逐条验（新增测试用例进 test:fast）
3. SKILL.md <500 行、references 一层深、无 README.md、frontmatter 全字段合规（写个结构校验脚本，对标开源 validate_skill.py）
4. 每个技能 ≥2 个真实 input/output 案例（用探针实测结果当案例，不用编的）

## 三、议题二：MCP 用量治理（Scale 开关）

### 3.1 现状与痛点

- MCP server 无任何连接级开关/配额（grep 实况：budget/quota/limit 零命中）
- 现有 skill-state.json 只管「技能启停」，不管「调用量」
- **token 大头在深读类工具**：read_full_book/get_chapter/read_range 一次可回几万字符；检索类次之；元数据类（list_books/list_catalog）几乎免费
- 外部智能体挂上后，agent 每次「想找依据」就调一次——不治理等于常开漏水

### 3.2 设计：三级暴露 + 定时窗口 + 会话预算 + 审计

**usage-policy.json**（与 skill-state.json 同目录同模式，H3 同款决策）：

```json
{
  "enabled": true,
  "schedule": {
    "workdays": ["09:00-18:30"],
    "weekend": false,
    "timezone": "Asia/Shanghai"
  },
  "budget": {
    "perSessionChars": 200000,
    "perSessionQueries": 30,
    "deepReadChars": 80000
  },
  "tiers": {
    "metadata": "always",
    "search": "gated",
    "deepRead": "budgeted"
  }
}
```

| 层级 | 工具 | 策略 |
|---|---|---|
| 元数据 | list_books/list_catalog/get_person/get_theme/list_skills/read_skill | **always 常开**（成本 ~0，让 agent 随时知道书架有什么） |
| 检索 | query_book/query_library/similar_chunks | **gated**：受 enabled+schedule 门控；每次调用计数 |
| 深读 | read_full_book/get_chapter/read_range | **budgeted**：门控 + 按返回字符数扣预算；超限返回 `{error, hint}`（对齐 lib 层铁律：不许 throw 穿层） |

**桌面层**：书架页加「知识库对外服务」开关 + 定时规则展示 + 当日用量条（已用字符/预算）；关闭态下 MCP 调 gated/budgeted 工具返回明确错误+提示，agent 收到后自然停止调用。

**审计**：usage-log.jsonl 落每次调用（时间/工具/书/字符数/命中还是拒收），与 feedback-export 并列一个新导出位；月底看「哪些书被查最多、哪些技能最常被触发」。

### 3.3 边界与不做

- 不做「按智能体身份鉴权」（单机本地优先产品，无多租户需求）
- 不做云端计费同步（本地优先，用量只落本地）
- 不动检索算法本身——本议题**纯加法**，不碰 routeAndSearch/hybridSearch，无需 eval-gate

### 3.4 验收标准

1. enabled=false 时三个层级行为正确（always 通 / gated 拒 / budgeted 拒），错误带 hint
2. 定时窗口外自动视为关闭（含时区与周末规则单测）
3. 预算超限拒收且计数准确（深读按字符扣）
4. 桌面 UI 开关/用量条与 usage-policy.json 双向同步
5. `npm test` + 全量 `npm run lint` 过；**外部智能体接入文档同步更新**（guard 22.6 防漂移断言会查——文档漏工具/漏配置门禁红）
6. 新增专用测试文件（开关/定时/预算三组用例）进 test:fast

## 五、待拍板项

1. W1/W2/W3 顺序是否认可（建议 W1 先堵漏水，W2 立规范，W3 铺技能）
2. 预算默认值是否合理（每会话 20 万字符 ≈ 一本中篇小说的量；深读 8 万字符/会话）
3. 定时窗口默认值（工作日 9:00-18:30，周末关）是否符合你的作息
4. 「opinion-archaeology」独立成 skill 还是并入 kb-research 场景表（我倾向独立：kk 触发词极清晰，且是清洗投入最大的独有资产）
