# V3-R7 模型可见性改造——全库审计与方案

> 2026-10-19。起因：老板提出「云端模型看不了全书，按现有索引方式没法当工具用；要不要全喂/从 MCP 全喂/按标签分类喂？token 爆炸怎么办？」
> 本文档 = 全库检索结果 + 对上一轮模型工作的对错判定 + 改造方案。所有数字均来自当日实测，非估算传闻。

---

## 一、结论先讲

1. **上一个模型做对了八成**：翻书工具其实已经建好了（`get_chapter` 整章通读 / `read_range` 区间读 / `lookup` 章节直达，V3-R5 的 browse.mjs），五路信号检索是 eval 93 分的成绩单，防幻觉红线（引用逐字回源）一直在有效工作。
2. **但「模型可见全书」确实没闭环**，缺的是三件小东西：**全文直读的入口**（小书被迫走检索，纯损耗）、**全书地图**（翻书缺第一跳）、**token 闸**（现有闸门按块数不按 token，对不同书行为差 20 倍）。
3. **改造不需要动检索引擎**，是「加入口 + 加闸门 + 补桌面对称性」，文件级清单见第五节。P0 三件预估半天。

## 二、事实盘点（本轮全库检索结果）

### 2.1 MCP 工具全景：14 个工具，其实分五类

| 类 | 工具 | 作用 |
|---|---|---|
| 导航 | list_books / list_catalog / get_person / get_theme / expand | 书架清单、编目（主题+人物+关系网） |
| 寻址 | lookup | 按章节标题/编号三级匹配直达 |
| **翻书** | **get_chapter / read_range** | **整章通读（60 块 cap）/ 按块号区间读（80 块 cap，带续读游标）** |
| 检索 | query_book / query_library / similar_chunks | 五路信号混合检索 + 自动挑书 + 以块找块 |
| 技能 | save_skill / read_skill / list_skills | 蒸馏手册落盘与按需加载 |

**关键纠正**：外部流传的「MCP 没有读原文的工具」是误判——翻书层在 V3-R5 就已建成，grep 时因注册形式是 `server.registerTool(...)` 而非对象字面量而容易漏检。

### 2.2 桌面问答链路（chat.mjs）

`cloudSummary` → `askWithRewrite`（查询改写，多问法）→ `ask/hybridSearch`（topN 默认 6）→ `askCloud`（buildMessages 把 6 个片段全文进 prompt，无长度截断）→ `verifyAnswer`（引用逐字回源）。

桌面侧**只有 top-k 检索一条路**，与 MCP 侧能翻章的能力不对称。

### 2.3 token 账（实测，7 本）

| 书 | 块数 | ≈token | chapter 列覆盖 |
|---|---|---|---|
| 论语·学而 docx | 16 | 0.5K | 16/16 |
| 论语·学而 pdf | 4 | 0.6K | 0/4 |
| 道德经 | 81 | 5.6K | 81/81 |
| attention 论文 | 51 | 9.6K | 0/51 |

一刀切全喂 = 每问一次 333K token，且超任何模型上下文上限——**这才是真爆炸**。

### 2.4 章节数据现实（实测）

| 书 | 章数（chapter 列） | 章均块 | 最大章 ≈token |
|---|---|---|---|
| P&P | 16 | 78 | 14K（**超 60 块 cap，必被截断**） |
| Frank | 30 | 24 | 12K |

章粒度在不同书之间差 20 倍以上；块数 cap（60/80）对大块英文章和小块中文章的行为完全不可比。

## 三、上一个模型做对了什么（判定：对）

1. **翻书层已建（V3-R5 browse.mjs）**：readChapter 三级匹配（精确→前缀→包含）+ 同级多命中取文档序 + 截断续读游标；readRange 区间读带空区间兜底。这是「模型能通读一章」的既有能力，方向完全正确。
2. **五路信号检索**（字面关键词 / 语义向量 / 编目提名 / enrich 提名 / 复试官终审）：大书（P&P 177.7K、Frank 104.7K）除了检索没有别的现实路径，这套是 eval 93 分的成绩单，不动。
3. **防幻觉红线**：引用逐字回源校验（verifyAnswer，子句命中率 ≥60%）、引擎卫兵、弱信号地板——问答可信度的地基。
4. **cap 防呆**：topN zod 20 上限、maxBlocks 60/80 上限、续读游标——「模型一次索要 999 条拖垮上下文」的场景已被堵住。

## 四、不足（判定：这是老板体感「没法当工具用」的根源）

| # | 不足 | 证据 | 后果 |
|---|---|---|---|
| 1 | **没有全文直读入口** | 14 个工具无 read_full_book；桌面 cloudSummary 只有 top-6 检索一条路 | 论语 16 块、道德经 81 块的书本可全文进上下文零误差，现在也走检索排序——小书检索是纯损耗，还可能漏 |
| 2 | **没有全书地图** | 无 get_outline；模型想知「本书几章、每章多大」只能靠 list_catalog（主题分布，不是章）或 get_chapter 的 not-found 回包（前 30 章名） | 翻书缺第一跳，模型不知道从哪章开始翻 |
| 3 | **cap 按块数不按 token** | CHAPTER_CAP=60 / RANGE_CAP=80；实测章均块从 3（孟子）到 78（P&P） | 孟子「按章喂」实际失效（3 块一章不够看）；P&P 大章被 60 块硬截；token 消耗不可预算 |
| 4 | **桌面与 MCP 能力不对称** | MCP 能 get_chapter，桌面只能 top-6 | 同一个「云端助手」，在桌面客户端里比在外部智能体手里弱一个档次 |
| 5 | **工具描述误导** | get_chapter 描述写「EPUB 章节值不可靠」，但 P&P/Frank chapter 列 100% 覆盖 | 调用方被描述劝退，明明能用的工具不用 |

## 五、改造方案（不动检索引擎）

### P0——核心补缺（预估半天，三件）

**① list_books 加 token 列 + 新增 read_full_book 工具**
- listBooks() 结果加 `total_tokens`（SUM(length(text)) × 语言系数：中文 0.75 / 英文 0.25）——调用方一眼看出哪本小书能直读
- `read_full_book(book)`：≤10K token 的书全文端出（论语 0.5K / 道德经 5.6K / attention 9.6K 四本立即受益）；>10K 返回 `{error:"too-big", tokens, hint:"用 get_outline + get_chapter/read_range"}`——**「权限全开」的正确形态：闸门按书体量自动开关**

**② 新增 get_outline 工具**
- 返回：全书章名列表 + 每章块数 + 每章 ≈token（按 chapter 列 GROUP BY）
- 这是翻书动线的第一跳：get_outline 看地图 → get_chapter/read_range 翻目标章

**③ browse cap 改 token 闸**
- browse.mjs 加 `estimateTokens(text)`；CHAPTER_TOKEN_CAP = 8K（token 为准，块数 cap 保留作硬上限）
- readChapter/readRange 返回体里带真实 token 账，续读游标按 token 给

### P1——对称性与描述（预估半天）

**④ cloudSummary 小书全文模式**
- bookId 指向的书 token ≤10K → 跳过检索，全书作 passages 直接进 askCloud（引用回源天然成立：verifyAnswer 的 target 就是原文）
- 开关 BSP_FULL_READ=0 可回退；注意 chat-fuzz 的 reqCount 精确断言要按既有惯例隔离
**⑤ 工具描述更新**：按 chapter 列实际覆盖率重写 get_chapter/read_range 描述
**⑥ stage3-mcp-test 工具清单硬断言同步**（加两个工具的既定排雷项）

### P2——质量验证（随考卷重建做）

**⑦** eval 考卷重建时加「全文直读 vs 检索」对照题（同一批题两种模式跑，量化小书收益）
**⑧** guard-test 第 20 节：read_full_book 闸门字面量 / get_outline 存在性 / token cap 常量

## 六、token 账：现状 vs 改造后

| 场景 | 现状 | 改造后 |
|---|---|---|
| 小书问答（论语/道德经/attention） | 检索 top-6 ≈2K + 排序误差风险 | 全文 0.5~10K，**零检索误差** |
| 孟子（33.7K，261 章） | 检索 top-6（章均 3 块，按章喂失效） | read_range 按需连续读 + 检索兜底 |
| P&P / Frank（>100K） | 检索 top-6 | get_outline 地图 → get_chapter/read_range 翻章 → 检索兜底 |
| 全库（模型自选） | query_library top-6 | 同上，按书自动分流 |

改造后没有任何场景需要「一次 333K 全喂」；小书成本几乎不变但**质量上限从检索天花板变成全文天花板**。

---

## 七、下一步建议

顺序：P0 ①②③（MCP 侧，外部智能体立即受益）→ P1 ④⑤⑥（桌面对称）→ P2 ⑦⑧（随 kk 收录与考卷重建）。
每步独立可回退（BSP_FULL_READ / token cap 常量），检索引擎零改动——现在的 eval 93 基线不会被这套改造动摇。
