## 二、5 处硬伤（会让执行卡住，已修订）

### B1 · 自己跟自己打架的红线

- **原文**：§5 红线 2 写「`package.json` 零新增」，§2.3、§7 又写「加 4 个 npm script」。
- **后果**：实施时不知道能不能改 `package.json`。
- **已改**：红线明确为「零新增**第三方依赖**」，4 条 script 属允许范围。

### B2 · 「lint 0」是个永远够不到的目标 ⚠️ 本轮新发现

- **实测**：全库 `eslint .` = **21852 errors / 23 warnings**（`no-undef` 8155、`no-unused-vars` 5001…）。
- **真实来源**：`runtime/mineru-python/Lib/site-packages/**` 下第三方前端 JS（gradio、fastapi_offline 等），而 `eslint.config.mjs:8-19` 的 `ignores` 有 `release*/**`、`node_modules/**`、`books/**`、`library/**`… **唯独漏了 `runtime/**`**。
- **另一个口径**：只看本轮改过的 11 个文件，`eslint` = **8 errors**，全在没改动过的老代码行（就是「验收就绪度评审」里等你定性的那 8 个）。
- **后果**：Phase 5 写「`lint 0`」当完成判据，等于要求清掉两万多个与项目无关的错误，不可能达成；方案里也没有任何对应措施。
- **已改**：加 `ignores` 补 `runtime/**`（一行配置）；判据拆成「本轮改动文件 0 新增错误 + 全库 lint 无 runtime 噪声」；8 个老错**由你拍板**定性，不擅自默认要修。

### B3 · 最要紧的一处：拿自己的卷子证明自己进步了

- **原文**：Phase 4 把「`routeAcc` 从 0.45 净提升」写成 M2 硬判据。
- **问题**：`routeAcc` 来自 `test/golden/` 那 80 题——正是方案 §2 自己判定为「自出题、自判分、不可证伪」的同源考卷。用它证明「路由改造有效」，等于绕了一圈又回到老问题。而且方案没写「没提升怎么办」。
- **已改**：**判据分离**——五项指标只作回归门禁（不退化即可），效果判定归 holdout 独立集 + 对照组；补上「未提升分支」：用 `--from-book/--from-route` 重放定位，回 Phase 2 调先验，既不硬判失败也不许静默调参。

### B4 · 方案自己会重犯这个项目最初的病

- **原文**：只在 M0（开工前）和 Phase 4（收工后）各拍一次存档照，中间 Phase 1/2/3 都在改代码，却没有任何留痕。

- **已改**：**每个 Phase 结束就重拍一次 + 台账追加**，形成 `c1b… → p1 → p2 → p3 → p4` 指纹链；明写「禁止 M0 与 Phase 4 之间出现无留痕的代码改动」。`生成清单.cjs` 已支持 `--id=`，零成本。
