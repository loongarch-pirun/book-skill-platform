## 3. 模块与数据结构

### 3.1 缓存条目（`vec-cache.mjs:17`）

```js
cache: Map<dbPath, {
  ids: Float64Array(n),      // chunk id，与 matrix 行号一一对应
  matrix: Float32Array(n*dim),// 所有向量首尾拼接（dim=1024）
  dim: number,                // 1024
  n: number,                  // 块数
  engine: string,             // "m3"（失效闸之一）
  mtimeMs: number,            // 失效闸之二
  size: number,               // 失效闸之三
  bytes: number,              // 占用量（LRU 预算用）= matrix + ids
  atime: number,              // LRU 最近使用
  centroid: Float32Array,     // **死字段**：建库时算、无人消费（本轮不动）
}>
```

内存量级：每块 `1024×4 + 8 = 4104` 字节 → 13 本 5,844 块 ≈ **22.9 MB**；20 本 ≈ 35 MB；默认上限 200 MB 可容纳约 51,000 块。

### 3.2 扫描结果行（`scanBookSem` 返回）

```js
rows: [{ id, kind, len, sem }]   // 两条分支产出的形状完全一致
```

`kind` 给「参考文献降权」用（`refW`），`len` 给碎片门槛（`minLen`）用 —— 这两个字段**不在矩阵里**，所以命中分支必须补一条轻量回表。

### 3.3 计数（本轮新增，纯观测）

`vecCacheStats()` 由 `{entries, mb}` 扩展为 `{entries, mb, hits, misses, disabled}`。
`disabled` = 「因为 cap=0 被跳过」的次数，用来区分「没命中」和「压根没开」。

## 4. 缓存键与失效策略

**键**：`dbPath`（绝对路径字符串）。
**失效四闸**（全部被动，不需要谁记得清缓存）：

| 闸 | 判据 | 触发场景 |
|---|---|---|
| 引擎 | `entry.engine === embedKey` | 换 `BSP_EMBED_MODEL` |
| 修改时间 | `entry.mtimeMs === stat.mtimeMs` | 重灌/重建该库 |
| 文件大小 | `entry.size === stat.size` | 同上 |
| LRU 容量 | `totalBytes + bytes > cap` 时逐出最老 `atime` | 书库变大超过上限 |

**关闭即旁路**：`BSP_VEC_CACHE_MB` 默认 0 → `cap<=0` → 清空并返回 `null`，调用方走旧分支。

**为什么不做主动失效**：`guard-test:1064-1067` 静态禁止 clean 四件 import `search.mjs | vec-cache | hybridSearch`，`:1147` 要求主动失效只能走 `inline-import.mjs` 的 `invalidateDownstream`。本轮不碰这条红线。

## 5. 读写流程

### 5.1 冷（首次访问某本书）

```
statSync(dbPath) → 比对失败 → 删除旧条目
SELECT id, emb FROM chunks WHERE emb IS NOT NULL      ← 一次性读全部 BLOB
逐行：Float32Array 视图 → matrix.set(v, i*dim)、ids[i]=id、（顺带累加 centroid）
bytes = matrix.byteLength + ids.byteLength → 超预算就逐出 atime 最老的
cache.set(dbPath, entry)
→ matrixScores(mat, qv, Map) → 轻量回表
```

### 5.2 热（缓存命中）

```
statSync → engine/mtime/size 三项全中 → atime 更新、hits++
SELECT id, kind, length(text) len FROM chunks WHERE emb IS NOT NULL   ← 不读 BLOB
对每个 id：sem = 点积(qv, matrix[i])（向量已归一化，点积即余弦）
```

### 5.3 数值一致性

两条分支都是「Float32 乘、double 累加、同一顺序」，所以结果**逐位相同**（`perf-test` 早有同类断言，本次又用 80 题严格比对复核，见 §7.1）。

### 8.3 性能验收（`node test/perf-test.mjs`，全部 PASS）

| 项 | 数据 | 说明 |
|---|---|---|
| 等价性 | 开/关 top-4 逐位一致 | `hybridSearch` 侧的同款保证 |
| 缓存建立 | 1 条目 5 MB，暖查询命中不扩容 | 条目复用正常 |
| **真实规模**（P&P 1250 块） | 关 37 ms vs 开 35 ms | **持平**，符合预期 |
| **大库**（2 万块合成库） | 关 67 ms vs **开 11 ms** | 每次查询免重读 **29 MB** BLOB，约 **6 倍** |
| 预筛路径 | 10 本书触发路由、`routed=4` 正常出结果 | P1 + P2 串起来不炸 |

### 8.4 一句实话：13 本规模下，缓存几乎不省时间

同条件 A/B 双跑（§8.1）说明得很清楚：**565.9 s vs 563.5 s，差 0.4%，在噪声里。**

原因不神秘——13 本书总共只有 22.9 MB 向量，逐行读 BLOB 本来就是毫秒级；而单题耗时的大头是**重排**（48 条 × ~128 ms ≈ 6 s）。缓存省下的是「读库」那一小截。

**所以 P2 的收益不是当下的，是为书库变大准备的**：2 万块（约 30 MB）时 67→11 ms 才是它的主场。当前这一轮真正的提速来自 P1 预筛（扫 13 本 → 扫 1 本）。

> 观察记录（不计入结论）：留出集三次跑分的单题均值为 8819 ms（P1 前）→ 6412 ms（P1 后）→ 4764 ms（P1+P2 缓存开）。第三个数受机器负载影响，**不作为缓存收益的证据**——严格证据只有 §8.1 的同条件双跑。

## 9. 边界情况与风险点

| # | 情况 | 现状 | 处置 |
|---|---|---|---|
| 1 | **默认关闭 ⇒ 收益要显式开** | `BSP_VEC_CACHE_MB=0` 是默认值 | 这是刻意的：内存上限与 WAL 盲区都还不可控。要变成默认开，得先有 §7.3 的命中率数据 |
| 2 | **WAL 写入窗口** | 主库 mtime/size 不变、`-wal` 里有数据时，缓存会给旧向量 | `graphrag-fuzz:502-524` 实证「close 即自愈」；编目/嵌入进程跑着时并发读最多看到旧值。可评估把 `ctimeMs` 纳入判据 |
| 3 | **混合维度坏库** | `assertEngine` 在 `getMatrix` 之前 → 先抛出、逐本记 `skipped_books` | 已由 `guard-test` 段 9/9b 钉死 |
| 4 | **kind/len 回表成本** | 命中分支多一条 `length(text)` 全表扫，是 O(n) 但不读 BLOB | 实测远轻于原路径；若成为瓶颈再评估「方案 B」（给 entry 加 kinds/lens，会牵动 `hybridSearch`，本轮明确不做） |
| 5 | **双进程各一份** | 桌面端与 MCP 端是不同进程，各有自己的 Map | 内存 ×2；13 本 22.9 MB 无压力，书库上百 M 时需按进程配额 |
| 6 | **LRU 抖动** | cap 小于「常用书向量总和」时，每次提问都在建/逐出 | 观测 `entries/mb` 是否贴着上限；调大 cap 或接受抖动 |
| 7 | **`centroid` 白算** | 建缓存时 O(n×dim) 累加，全库无消费点 | 本轮不动（定稿已排除质心粗筛）；留作技术债 |
| 8 | **只读库句柄** | 所有检索入口 `readonly:true`；Windows EBUSY | 未改 |
| 9 | **缓存不落盘** | `search.mjs:40` 早已否决写盘（双进程打架、WAL 盲区） | 保持不落盘 |
| 10 | **主动失效被禁** | clean/inline 链路不许 import `clearVecCache` | 靠被动失效；真要主动清，只能由 `jobs.mjs`/IPC 在事务提交 close 后调 |
