# 验收 vs 全量评审：优先级决策单

> 2026-11-15 · 知库视角（评测与质量度量 / 治理运营）  
> 结论先行：**先做「验收就绪度评审」（限定范围、半天），然后立刻跑验收；全量评审放最后。**  
> 若必须二选一，选**评审**——但不是「全量重写式评审」，是半天内把尺子定准。

---

## 0. 一句话理由

**这个项目的测量标准本身是坏的。** `test/quality-gate.mjs:642` 用 `now >= b` / `now <= b`，基线=当前时五项恒绿、零检出能力；`_final-gate.log` 的「✓ 五项未退化」就是这样重放出来的。拿一把已~~知会报假绿的尺子去跑完整验收，量出来的结果不能作为决策依据。~~

~~先定评测集与指标口径（eval set + metric contr~~act），再跑 eval，是 RAG 知识库治理的标准顺序。反过来做，等于再次验证「尺子没坏」而不是「系统没坏」。

## 2. 两条路对比

| 维度      | 先跑完整验收                                                    | 先做验收就绪度评审                       |
| ------- | --------------------------------------------------------- | ------------------------------- |
| 短期收益    | 拿到「当前能不能跑」的事实，但**多半不可解释**（假绿 / 假红分不清）                     | 把「什么算通过」定下来，后续每一次验收都可判读         |
| 长期收益    | 低：这次绿了，下次改完还得重来                                           | 高：一次定口径，长期复用；对应评测集 + 指标契约       |
| 误判风险    | **高**：闸门恒绿、lint 存量错误未定性、`win-unpacked` 缺失必然红              | 低：先区分「真坏了」与「本来就这样」              |
| 环境风险    | 高：全库 lint / `test:fast` / 模型加载已两次被 SIGTERM；`dist` 重打 1.8G | 低：只读为主，无重资源动作                   |
| 对存档照的影响 | 验收会写 `quality-gate-run.log`、改 `release/`，树指纹变、台账对不上       | 无写入，存档照不动                       |
| 对当前病灶   | 可能加重（又一份没有依据的绿灯）                                          | 对症（先定标准，不叠文档）                   |
| 主要风险    | 白跑 + 误判                                                   | **容易拖成「只出文档不动手」** → 用时间盒与范围约束压住 |

## 3. 依赖关系：不是二选一，是夹心

```
验收就绪度评审（定尺子、定前置）
        ↓ 提供判据
分批次完整验收（拿事实）
        ↓ 提供异常清单与事实锚点
全量评审（只评暴露出来的模块 + 框架扩展位）
```

- **验收依赖小评审**：不知道合格线、不知道哪些是存量债、不知道哪些产物允许被覆盖，跑完无法判读。
- **全量评审依赖验收**：刚做完方案 A、代码树动过；现在通读全部源码，会把「运行问题」和「架构问题」混在一起。验收给出的异常清单，才是评审该重点看的地方。
- 所以「先全量评审」两头不靠：既没有事实锚点，又会把定标准的事拖到最后。

## 4. 推荐执行顺序（4 步，每步有可验证产出）

| 步     | 做什么                                                                                                                       | 时间盒     | 完成判据（产出物）                                | 写入位置                               |
| ----- | ------------------------------------------------------------------------------------------------------------------------- | ------- | ---------------------------------------- | ---------------------------------- |
| **1** | **验收就绪度评审**：只回答 4 个问题——① 验收判据是什么 ② 哪些是存量债、不阻塞本轮 ③ 前置条件齐不齐 ④ 验收会写哪些文件、怎么留档                                                 | 半天，只读为主 | 一张 8 项前置清单（见 §6）+ 一张判据表                  | 本决策单勾完 → 结果追加进 `改动台账.md`，**不新建报告** |
| **2** | **批次 A 验收**（快、无模型、不改产物）：分目录 lint 定性 8 个存量错、`judge-test`、`golden-verify`、`test:ci` 子集、`生成清单.cjs --check`                   | 30 分钟   | 带时间戳的跑批记录 + 红绿逐条归因                       | `改动台账.md` 新增条目                     |
| **3** | **批次 B+C 验收**（重资源 / 会改产物）：闸门现跑 + `--topN=1` 翻转 + `test:fast` 关键子集；`npm run dist` 前先重建 `win-unpacked` 再跑 `packaged-verify` | 半天～1 天  | 带日期、带 exit code 的验收报告；跑前重拍存档照、跑后登记台账与树指纹 | 台账 + 新树指纹                          |
| **4** | **全量评审**：只评「验收暴露的模块」+ 框架扩展位（分类树、元数据 schema、chunking / embedding / rerank 的可演进性）                                           | 单独一轮    | 一份架构评审，复用已有 5 份报告结论，**不重写历史**            | 一份文档，不新建体系                         |

**批次 B 的硬前置**：跑之前先把 `quality-gate-run.log` 留档，并明确「本次允许覆盖」；否则 11-14 那 8 个日志的追溯链断掉。

## 5. 为什么这样排（4 条理由）

1. **尺子坏了，量了也白量。** `>=`/`<=` + 基线=当前 = 假绿。项目已经吃过一次亏（`_final-gate.log` 是 `--from` 重放、没跑检索函数）。先跑会复制同一个错误。
2. **前置缺失会造成假红。** `win-unpacked` 不存在 → 打包验收必然 FAIL；lint 8 个存量错未定性；baseline inputs 在 r4 之外 → 结果不可复现。不先定性，跑完分不清「真坏了」和「本来就这样」。
3. **验收会改产物、破坏存档照。** 闸门现跑覆盖 `quality-gate-run.log`，`dist` 重打 release。不先约定留档方式，树指纹一变，84 条台账就对不上。
4. **全量评审需要事实锚点。** 刚做完方案 A，现在通读源码评架构，会把运行问题和架构问题混为一谈；而且第 7 条显示文档已达 40 份，此时堆长报告与「机制混乱」的病灶相冲。

## 7. 明确答案

- **先做哪一项**：第 1 步「验收就绪度评审」。
- **不是**：先跑完整验收（尺子坏、前置缺、会改产物）。
- **也不是**：现在做全量评审（无事实锚点、会加重文档通胀）。
- **全量评审放第 4 步**，等验收给出异常清单再开始。

一句话：**先把「什么算通过」写死，再去跑；跑完拿事实，再回头评架构。**
